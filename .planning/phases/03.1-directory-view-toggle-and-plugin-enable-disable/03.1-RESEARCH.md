## Summary

This phase has two distinct sub-problems. The first is a pure client-side data transformation: `buildItemMaps` in `ArtifactTree.tsx` produces a scope > category > leaf hierarchy; a parallel `buildDirectoryItemMaps` function must produce a filesystem path hierarchy instead. The raw data to drive it (full `absolutePath` on every `Artifact`) already exists — no server changes are needed for the view toggle itself.

The second sub-problem is a surgical server-side mutation: read `~/.claude/settings.json`, toggle a plugin name inside the `enabledPlugins` array, and write back atomically. `write-file-atomic` is already a project dependency. The risk surface is narrow: the safety gate (only act if `enabledPlugins` already exists) prevents any schema corruption.

The UI-SPEC (approved 2026-03-30) has already resolved all discretionary design questions. Both features are purely additive — no existing behavior is removed or changed.

**Primary recommendation:** Build `buildDirectoryItemMaps` as a standalone function alongside the existing `buildItemMaps`, add a `viewMode` state variable to `ArtifactTree.tsx` backed by `localStorage`, and add a new `POST /api/operations/toggle-plugin` route following the exact same Zod + Fastify pattern as existing operation routes.

## Architecture Patterns

### Pattern 1: Dual buildItemMaps

The existing `buildItemMaps` (scope > category > leaf) stays untouched. A new `buildDirectoryItemMaps` function accepts the same `ScopeNode[]` input and produces the filesystem hierarchy. The caller in `ArtifactTree.tsx` switches between them based on `viewMode`.

**Key algorithm for `buildDirectoryItemMaps`:**
1. For each `ScopeNode`, extract the filesystem path segments between the common ancestor and the `.claude/` directory from `scope.rootPath` and each `artifact.absolutePath`.
2. Build a trie of path segments; each non-Claude directory becomes a `nodeKind: 'folder'` node.
3. Claude artifact containers (`.claude/`) become scope-like nodes, and artifacts nest under them directly (no category grouping in directory view — artifacts hang at the leaf level under their type directory as folder nodes, or flat under `.claude/` node per the Finder metaphor).
4. Global scope is always inserted as the first root child, regardless of filesystem position.

```typescript
// New nodeKind for non-Claude ancestor folders
export type TreeNodeData =
  | { nodeKind: 'root' }
  | (ScopeNode & { nodeKind: 'scope' })
  | { nodeKind: 'category'; id: string; type: ArtifactType; label?: string; children: Artifact[]; count: number }
  | { nodeKind: 'folder'; id: string; label: string; absolutePath: string }
  | (Artifact & { nodeKind: 'leaf' });
```

The `isItemFolder` predicate in `useTree` already checks `nodeKind !== 'leaf'` — folder nodes will work with zero changes to headless-tree setup.

### Pattern 2: viewMode state + localStorage

```typescript
// In ArtifactTree.tsx
const [viewMode, setViewMode] = useState<'flat' | 'directory'>(() => {
  return (localStorage.getItem('cdt_view_mode') as 'flat' | 'directory') ?? 'flat';

const handleViewModeChange = (mode: 'flat' | 'directory') => {
  setViewMode(mode);
  localStorage.setItem('cdt_view_mode', mode);
  // Reset expansion state per CONTEXT.md
  tree.applySubStateUpdate('expandedItems', () => mode === 'flat' ? scopeIds : topLevelFolderIds);
  tree.rebuildTree();

```

The `{ items, children }` memo already switches automatically once `buildDirectoryItemMaps` is called conditionally:
```typescript
const { items, children } = useMemo(
  () => viewMode === 'flat' ? buildItemMaps(filteredScopes) : buildDirectoryItemMaps(filteredScopes),
  [filteredScopes, viewMode]
);
```

### Pattern 4: toggle-plugin server route

Follow the exact same pattern as `POST /api/operations/copy` in `src/server/routes/operations.ts`:

```typescript
// Request schema
const TogglePluginRequestSchema = z.object({
  pluginName: z.string(),
  settingsPath: z.string(), // absolute path to ~/.claude/settings.json
  enable: z.boolean(),
});

// Route handler logic
const raw = await fs.readFile(settingsPath, 'utf-8');
const settings = JSON.parse(raw);
if (!settings.enabledPlugins || !Array.isArray(settings.enabledPlugins)) {
  return reply.code(400).send({ success: false, error: 'enabledPlugins field not found' });
}
if (enable) {
  if (!settings.enabledPlugins.includes(pluginName)) {
    settings.enabledPlugins.push(pluginName);
  }
} else {
  settings.enabledPlugins = settings.enabledPlugins.filter((p: string) => p !== pluginName);
}
await writeFileAtomic(settingsPath, JSON.stringify(settings, null, 2));
return { success: true };
```

### Directory View Filter Behavior

`deriveVisibleTree` returns `ScopeNode[]` with filtered artifacts. `buildDirectoryItemMaps` consumes this filtered output — it never needs to know about the filter itself. Ancestor folder nodes must be preserved when any descendant artifact matches, which happens naturally since the trie is built from whatever artifacts survive the filter.

### Anti-Patterns to Avoid

- **Don't modify deriveVisibleTree**: It operates on `ScopeNode[]` and outputs `ScopeNode[]`. Both views consume its output. No view-mode logic goes inside it.
- **Don't use optimistic update for plugin toggle**: CONTEXT.md explicitly requires full tree refresh.
- **Don't create settings.json or enabledPlugins**: The route must return an error (not create) if the field is absent. The client must never show the toggle UI in that case.
- **Don't merge the section header logic into directory view**: Section headers (`Current Project`, `Other Projects`) are flat-view-only. Directory view renders plain folder nodes with no section headers.

## Common Pitfalls

### Pitfall 1: Common ancestor computation for directory view

**What goes wrong:** If two projects live at `/Users/furqan/Documents/Projects/A` and `/Users/furqan/Documents/Projects/B`, the common ancestor is `/Users/furqan/Documents/Projects`. But if one project is at `/Users/furqan/Documents/Projects/A` and global is at `/Users/furqan/.claude`, computing a common ancestor that includes global would create a deeply-nested tree starting from `/Users/furqan`.

**How to avoid:** Global scope is always rendered as a top-level root node (separate from the filesystem tree), per the locked decision. Only project scopes participate in the common ancestor computation. Compute the common ancestor across `scope.rootPath` values for all project scopes only.

**Warning signs:** Tree shows `/Users` or `/` as root node.

### Pitfall 2: Stale tree instance after viewMode change

**What goes wrong:** `tree.rebuildTree()` must be called after switching viewMode, otherwise headless-tree will keep the old `expandedItems` IDs which may not exist in the new item map, causing silent no-ops or phantom expanded states.

**How to avoid:** Call `tree.applySubStateUpdate('expandedItems', ...)` then `tree.rebuildTree()` inside `handleViewModeChange`, same pattern as the existing `handleToggleExpand`.

### Pitfall 3: Plugin name vs artifact name

**What goes wrong:** The `enabledPlugins` array in `settings.json` stores plugin names as strings. The scanner uses the parent directory name as the plugin artifact name (e.g., `test-plugin` from `plugins/test-plugin/`). These must match exactly — case-sensitive.

**How to avoid:** Pass `artifact.name` directly as `pluginName` to the toggle route. Never derive it from the path.

### Pitfall 4: JSON.parse of malformed settings.json

**What goes wrong:** If `settings.json` has trailing commas or comments, `JSON.parse` throws. The route crashes with a 500 instead of a clean error.

**How to avoid:** Wrap `JSON.parse` in try/catch in the route handler. Return `{ success: false, error: 'settings.json is not valid JSON' }` with a 400 status. Include the 400 response schema in the Zod route definition (known pattern from Phase 3 decision: "400 response schema must be declared alongside 200").

### Pitfall 5: nodeKind 'folder' breaks getItemName

**What goes wrong:** `useTree`'s `getItemName` callback currently handles `scope`, `category`, `leaf`, `root`. A new `folder` nodeKind without a case will fall through to `return 'root'`, producing incorrect accessibility labels.

**How to avoid:** Add `if (d.nodeKind === 'folder') return d.label;` to the `getItemName` handler.

### Pitfall 6: environmentMatchGlobs in vitest.config.ts is already removed

The config uses `environmentMatchGlobs` (`[['tests/**/*.tsx', 'happy-dom']]`) but the project decision log notes "environmentMatchGlobs removed in vitest 4.x". Check: the current `vitest.config.ts` still uses `environmentMatchGlobs`. Any new `.tsx` test files must use the `@vitest-environment happy-dom` docblock instead.

## Code Examples

### Common ancestor path computation
```typescript
// Source: standard path algorithm, applicable to node:path.posix
function commonAncestor(paths: string[]): string {
  if (paths.length === 0) return '/';
  const parts = paths.map((p) => p.split('/'));
  const shortest = Math.min(...parts.map((p) => p.length));
  let i = 0;
  while (i < shortest && parts.every((p) => p[i] === parts[0][i])) i++;
  return parts[0].slice(0, i).join('/') || '/';
}
```

## Open Questions

1. **settings.json location for project-scoped plugins**
   - What we know: Global plugins live at `~/.claude/plugins/` and the `enabled` field on the artifact reflects `~/.claude/settings.json`. The scanner sets `enabled` based on `enabledPlugins` in `~/.claude/settings.json`.
   - What's unclear: Does a project `.claude/` directory ever have its own `settings.json` with `enabledPlugins`? If so, the toggle route needs to know which `settings.json` path to write.
   - Recommendation: Pass `settingsPath` explicitly from the client. The client resolves it as `scope.rootPath + '/settings.json'` — the server treats it as an opaque path, applies the same safety gate, and writes atomically. No hard-coding of `~/.claude`.

2. **Directory view: .claude folder node visibility**
   - What we know: The hierarchy should be `ProjectA > .claude > commands > foo.md`.
   - What's unclear: Should `.claude` itself be a navigable folder node (with a chevron), or should project scope jump directly to artifact type directories?
   - Recommendation: Render `.claude` as a folder node. This is consistent with the Finder metaphor and makes the structure literally match the filesystem. Users familiar with Claude's directory layout will immediately recognize it.
