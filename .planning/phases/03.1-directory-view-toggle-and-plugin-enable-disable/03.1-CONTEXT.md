# Phase 3.1: Directory View Toggle & Plugin Enable/Disable - Context

**Gathered:** 2026-03-29
**Status:** Ready for planning

<domain>
## Phase Boundary

Two features: (1) a flat/directory-hierarchy view toggle so users can see artifacts organized by filesystem path instead of scope-first grouping, and (2) plugin enable/disable via context menu and detail panel, writing to ~/.claude/settings.json. No new artifact types, no new file operations.

</domain>

<decisions>
## Implementation Decisions

### Directory hierarchy structure
- Full filesystem paths as the tree structure: ~/Documents/Projects/ > ProjectA > .claude > commands > foo.md
- Only recognized Claude artifacts shown (no unknown files/folders inside .claude/)
- Common ancestor directories merged into a single tree (projects sharing ~/Documents/Projects/ appear as siblings)
- Non-Claude folders on the path to a project render as plain folder nodes
- Global scope (~/.claude/) rendered as a separate root at the top, not inline at filesystem position
- No "Current Project" section in directory view (that concept only exists in flat view)
- Current project folder gets a subtle "current" badge in directory view for discoverability

### View toggle UX
- Toggle lives in the tree bar (same row as expand/collapse and scope count), NOT in the search toolbar
- Both the view toggle and expand/collapse are tree-structure controls, grouped together
- Exact layout and icon treatment: Claude's discretion
- Switching views resets expansion state to defaults (flat: scopes expanded/categories collapsed; directory: top-level expanded/rest collapsed)
- Search and type filter work identically in both views (filter artifacts by name/type, preserve ancestor path context)

### Plugin toggle interaction
- Enable/disable available via context menu action AND detail panel action (two access points)
- No inline toggle switch in the tree rows
- Current visual UX maintained: green "enabled" badge, grey "disabled" badge on plugin nodes (already implemented in TreeItem.tsx)
- Disabled plugin children render normally (no dimming), badge only on plugin node
- After toggling, full tree refresh triggered (not optimistic update)

### Plugin toggle safety
- Only show enable/disable action when settings.json exists AND has an enabledPlugins field
- If settings.json doesn't exist or lacks enabledPlugins: no toggle action shown at all
- Never create settings.json or the enabledPlugins field from scratch
- Read-modify-write with atomic write (write-file-atomic) for settings.json updates

### Persistence
- View preference (flat vs directory) stored in browser localStorage
- Persists across sessions, lost on browser data clear (acceptable)

### Claude's Discretion
- Tree bar layout arrangement for view toggle + expand/collapse + scope count
- Icon choice for flat vs directory toggle
- Directory view default expansion depth
- How ancestor folder nodes render (plain folder icon, muted style, etc.)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `TreeItem.tsx`: Already renders plugin enabled/disabled badges (green/grey). nodeKind discriminant union handles scope/category/leaf rendering.
- `ArtifactTree.tsx`: buildItemMaps creates the flat view tree. Tree bar area with expand/collapse + scope count is the target for the view toggle.
- `deriveVisibleTree.ts`: Filter logic works on ScopeNode[]. Directory view will need its own derivation function or an adapted version.
- `write-file-atomic`: Already a project dependency for safe file writes.
- `ContextMenu.tsx`: Action dispatch pattern exists for copy/move/promote/demote. Plugin toggle follows same pattern.
- `showToast()`: Module-level subscriber for toast notifications.

### Established Patterns
- headless-tree with syncDataLoaderFeature for tree rendering
- buildItemMaps converts ScopeNode[] into flat items + children maps for headless-tree
- TreeNodeData union type with nodeKind discriminant ('root' | 'scope' | 'category' | 'leaf')
- Zod schemas on server, plain TypeScript types on client
- Atomic writes via write-file-atomic for all filesystem mutations

### Integration Points
- Directory view needs a new buildItemMaps variant that creates filesystem hierarchy instead of scope > category > leaf
- May need a new nodeKind (e.g., 'folder') for non-Claude ancestor directories
- Plugin toggle needs a new server endpoint to read/write settings.json enabledPlugins
- ContextMenu needs conditional "Enable"/"Disable" action for plugin-type leaves
- ArtifactDetailPanel needs the same toggle action
- localStorage for view preference (new, no existing localStorage usage to reference)

</code_context>
